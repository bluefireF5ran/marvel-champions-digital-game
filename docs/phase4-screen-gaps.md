## 0. Sources and ground rules

**Canvases** (all in `Marvel Champions game screens/`):

- `Screens - Desktop.dc.html`: sections 00 (flow map) to 14. Section numbers below (`D02`, `D13`…) refer to these.
- `Screens - Phone.dc.html`: `P01`–`P17`.
- `Screens - Tablet.dc.html`: `L01`, `L02`, `P01`, `P02`, `L05`–`L08`. Its portrait screens are also numbered `P01`/`P02`, so they are cited here as `T-P01`/`T-P02`.
- `Board - Long Table.dc.html`, `Board - Phone.dc.html`: the board.
- `Components.dc.html`: the design system.

**Ground rules, unchanged from Phase 4:**

- **Phaser is a view, never an authority.** Every rules fact on these screens (legality, damage, threat, deck legality) comes from `@mc/engine`. A screen that needs a fact the engine doesn't expose waits for an engine query (§2). It never computes the fact itself.
- **The mocks' card text is placeholder** (PLAN.md Phase 4, "Design source"). Names, stats and rules text come from `@mc/content`. See §5 for the mock content that is wrong for the Core Set.
- **Dashed = not yet real.** An action a screen shows before it exists is drawn unavailable with its reason, not omitted. Game Over already does this.
- **Hidden information stays hidden.** Previews and advice must use only what the deciding player may see (`view/visibility.ts`). A facedown boost card is a range, never a peeked value.
- **"Seat · AI" is "Seat · you"** (PLAN.md Phase 4, hero seats). Hero AI is Phase 8 backlog.
- New view models are plain TypeScript with Vitest tests, and scenes stay thin (PLAN.md Phase 4).
- **Match the canvases' look, not just their parts (added 2026-09-17).** Every screen workstream reads the rendered canvases for its screens (all three form factors) before building and finishes with side-by-side screenshots — [design-reference.md](design-reference.md) has the renders, a tile index and the procedure. The tokens and `Mc*` widgets already exist; what has been missing is each screen's composition (grounds, split, hierarchy, density).

    - **How `legalActions` probes, and what a probe costs.** `probe()` (`packages/engine/src/legal.ts:108-111`) is the whole mechanism: it calls `applyCommand(state, command, deps)` and keeps only `ok` / `error.code` / `error.message`, throwing the resulting state away. `evaluate` (`legal.ts:220-271`) runs one probe per (target × wallet) variant and turns the failures into `blockedTargets`. It works because `applyCommand` is pure (`engine.ts:22-43`) and `Ctx.state` is _replaced_, never mutated (`ctx.ts:15-21`, `updateInstance`/`moveCard`/`setFrame` all rebuild), so a probe cannot touch the caller's state — RNG included, since `RngState` is a field of `GameState` (`state.ts:298`). Cost: `legal.ts:588-598` records 5–8 ms for a whole `legalActions` (which is dozens to hundreds of probes) and 0.3 ms for `paymentFor`, so a single probe is well under 1 ms. A 10-target preview is a handful of milliseconds, and the client already runs the engine off the main thread in `EngineHost`'s worker. No caching, no memoization: a preview is cheap and must always be computed against the state as it is right now.

    - **S5.2 The diff is derived from the events, with totals read off the two states — not from a structural state diff.** Both were considered; events win for three reasons. (1) A numeric diff of `instances` says `damage: 9 → 14` and cannot say _why_, but the engine already emits the distinctions the design asks for: `damagePrevented{reason:"tough"|"cancelled"|"effect"|"cannotTakeDamage"}` (`events.ts:25`), `overkillSpilled` (`:98`), `threatRemovalBlocked` (`:118`), `uniqueEntryBlocked{disposition}` (`:109`), `leavePlayBlocked` (`:120`), `activationSkipped{reason}` (`:37`), `statusRemoved{reason}` (`:32`), `hitPointsSet` as distinct from `damageHealed` (`:31`, `:29`). "Toughness absorbed it" and "the excess was lost for want of overkill" are literally an event and the _absence_ of one. (2) Events carry order; a state diff doesn't, and order is what the player is being asked about. (3) A generic `GameState` differ would need maintaining forever as the state shape grows, and would happily surface deck order — a hidden-information hazard by default. Returning the events themselves rather than a parallel `PreviewChange` union also means `view/log-lines.ts` already words every one of them (`log-lines.ts:205-213` is exactly "ATK 3 + 2 boost − 1 defense"), so W5's panel is mostly `logLine` in the future tense, and a new event kind flows through without an engine change. That is the _structured, not strings_ part: `OutcomePreview` contains no prose.
      What events can't give is a total, because adding damage to a max-HP is a rule. So `counters` carries before/after for every instance the events named, each side read through the engine's own existing selectors (`remainingHitPoints`, `characterProfile`, `mainSchemeValue`, `query.ts`) — the same functions the live board reads — against the pre-state and the probed state. "14 HP → 9 HP" and "defeated" come from `counters`; "Toughness absorbed it", "Guard cleared", "no overkill, so the rest was lost" come from `events`. Nothing is recomputed and no rule is restated.

    - **S5.3 Where a preview stops.** Three stops, in the order they're checked:
      - **A nested choice.** Free: `applyCommand` returns as soon as `runFlow` parks a `PendingChoice` (`engine.ts:31-38`), so the probe halts there by construction. Report `stop: {kind:"choice", prompt, playerId, soleDecider}` so the panel can say "…and then you'll choose a target". **The preview never auto-answers a nested choice.** Auto-answering would be the engine deciding, and would be wrong exactly when the answer matters. If W5 later wants "and then, whichever you pick, …", that is the client calling `preview` again on each answer — a tree it builds, not one the engine invents.
      - **An interrupt/response window.** Falls out of the same rule and lands on the right side of it. A _forced_ interrupt or response resolves inside the probe with no choice parked, so a Forced Interrupt that changes the attack _is_ in the preview — correct, since it is mandatory and public (RRG 1.8 p. 5 "Ability — Simultaneous Timing Priority"; attack step 6, p. 9). An _optional_ window parks `chooseTriggers` (`choices.ts:43`, `resolve/window.ts`) and stops the preview, which is also correct: whether another player uses a card is not something the engine may predict. One consequence to word in the UI: a preview is what happens _if nobody responds_.
      - **Hidden information.** The probe walks the real state, so left alone it would compute the true post-flip damage and the true drawn card. The guard is a truncation rule stated over zones, not over a hand-maintained list of "risky" event types, so it can't rot:
        1. classify every instance against the **pre-probe** state — _zone-hidden_ if it is in a player deck, an encounter deck or a separate deck that the deciding player is not already being shown (the same "a deck is closed except for what an open decision offers" rule `view/visibility.ts` states for the client; the engine should own the predicate and the client's `faceVisible` should delegate to it rather than the two forking); _face-hidden_ if it is out of a deck but `faceup === false` (a facedown boost card, a dealt encounter card, a facedown Drone, a tucked card, a set-aside nemesis set);
        2. truncate `events` at the first event that (a) names a zone-hidden instance, (b) turns a face-hidden instance faceup, or (c) follows a change in `state.rng`;
        3. report `stop: {kind:"hiddenInformation", after}`.
           So the honest answer to "the outcome depends on hidden info" is **a certain prefix plus an explicit unknown**, never a peeked answer. This is also what keeps `preview(endTurn)` from narrating a whole villain phase: it stops at the first dealt encounter card.
      - **Rejected.** If `applyCommand` refuses, `stop: {kind:"rejected", reason, message}` carries the engine's own code and message, the same pair `legal.ts:110` produces. That is what the target list dims a target with when it was reached some other way.
      - **The invariant to test, not merely argue:** an effect could _read_ a hidden card without emitting an event that names it ("if the top card of your deck is a Weapon, deal 2"). Rules 1–3 wouldn't catch that. So the binding property is **permutation invariance**: shuffling the cards within any hidden zone must not change a single byte of the returned `OutcomePreview` (RRG 1.8 p. 27 "Look, Looked-At" — only a player an ability instructs to look may see those cards; p. 15 "Deck" and p. 17 "Encounter Deck" — deck order is fixed but not readable). It is cheap to test over a corpus and it is the test that finds the one card that breaks the zone rule; when one does, that effect kind gets marked hidden-dependent rather than the rule being loosened.

    - **S5.4 Determinism and replay.** A preview is a query, never a command. `GameLog` only grows through `sessionApply` (`engine.ts:189-201`) and `appendCommand`; `preview` calls `applyCommand` directly and discards the state, exactly as `probe` does, so a preview cannot enter the log, cannot advance `state.rng`, cannot advance `nextChoiceSeq`/`nextFrameSeq`, and is invisible to `replay()` and to `auditVillainPhases`. Two tests hold that: the passed-in state deep-equals a clone taken before the call, and a session that runs previews between commands produces a byte-identical `GameLog` to one that doesn't.

    - **S5.5 Defend preview: a range, computed ahead of the hidden cards.** `preview` is useless for the defend choice — it would truncate at the first `boostCardFlipped` — so the range is its own query, and it is the **one** place the engine does arithmetic in front of hidden cards. That is only allowable because the answer is permutation-invariant over them. New file `packages/engine/src/defend-preview.ts`:

      Null unless the open `PendingChoice.prompt.kind === "declareDefender"`; the attack is read off the frame `PendingChoice.frameId` names (`choices.ts:124`; the choice is requested with `frameId: frame.frameId`, `resolve/enemy-activation.ts:280`).
      - **What "public" means here, precisely.** The **count** of facedown boost cards is exact and public, not a guess: the procedure gives them at stage `giveBoost` and only then moves to `declareDefender` (`enemy-activation.ts:213-219, 246-282`), matching RRG 1.8 p. 9 steps 1–2, so at the moment the choice is open every boost card for this attack is already on the enemy and `mustInstance(state, enemyId).boostCards.length` is the final number — additional ones from `extraBoost` and any dealt outside an activation (p. 11) included. The **icons on each card** are not public until the card is flipped in step 3 (p. 9, p. 11). The **composition of the unseen pool** is public: the players assembled the encounter decks themselves at setup, and "Each discard pile is open information, and may be looked at by any player at any time" (p. 16 "Discard Pile"), so _which_ cards remain unseen is legitimately derivable; only their order is secret (p. 15 "Deck", p. 17 "Encounter Deck").
      - **The bound.** Pool for a given facedown card = every instance still in its home encounter deck (`CardInstance.home` / `discardZoneFor`, so multi-villain decks don't get mixed) **plus** every still-unrevealed facedown card that came out of that deck (the boost cards themselves, undealt-but-facedown encounter cards) — they are all equally unknown, and the k boost cards were drawn from exactly that multiset. If that pool is smaller than k, add the deck's discard pile, which is what a reshuffle would put back (p. 17). Then `max` = the sum of the k largest `boostIconsFor(state, deps, candidate)` over the pool and `min` = the sum of the k smallest, taken without replacement because each boost card is a distinct card. Using `boostIconsFor` (`modifiers.ts:107-123`) rather than the printed `boostIcons` is deliberate: a card in play can modify boost icons, and the preview must not restate that rule. The printed range is 0–3 (`content/src/schema/validation.ts:184-187`), so `3 × k` is available as a trivially safe fallback and `scope: "wholeSet"` (bound over every card in the assembled decks, seen or not) as a looser but unimpeachable one — `"unseen"` is the default. **Flagged, not silently decided:** the RRG never says in so many words that the encounter deck's _contents_ are open information. It follows from how the deck is built plus the open discard pile, and every real player counts this way, but it is the one rules-adjacent judgement in S5; `scope` exists so the call can be changed in one place if the user wants the weaker claim.
      - **Boost abilities are never folded into a number.** A star icon marks a mandatory "Boost" ability (p. 11; p. 40 "Star Icon") that can do anything, and p. 11 is explicit that a star is _not_ a boost icon and that damage dealt by a boost ability is not damage dealt by the activation — so a numeric ceiling that tried to include it would be dishonest twice over. The preview reports `mayTriggerBoostAbility` plus `poolWithBoostAbility` / `poolSize` (permutation-invariant counts; no card is named, and no probability is computed — that would be advice, which §4 hasn't settled) and the client words it "one of these may also carry a Boost ability". `bands` covers icons only.
      - **Bands, not a bare min/max.** The outcome can _change kind_ across the range, so the query walks every integer boost total in `[min, max]` (at most `3k + 1` values) and collapses equal outcomes into bands. That is how "5–7 damage, and at 6 or more Spider-Man is defeated" gets said without the client doing arithmetic.
      - **The arithmetic itself is not restated.** `damage = max(0, atk + boostIcons − reduction)` lives inline in `enemy-activation.ts:298-312`, together with the two rules that surround it: a dashed ATK is an unmodifiable 0 so `vars.atkBonus` doesn't raise it (p. 15 "Dash (Value)"), and `reduction` is the defender's DEF **only** when `basicDefense && defenderProfile.kind === "identity"` (p. 9 step 4 and p. 15 — an ally's DEF never reduces; all the damage is dealt to the ally, and without overkill nothing carries over, p. 9 step 5). Extract that block as an exported pure `plannedAttackDamage(state, deps, frame, { boostIcons, defenderInstanceId, basicDefense })` and have `executeEnemyAttackFrame` call it with the real flipped total. One implementation, two callers, no drift.
      - **Status interactions, only where they change the public arithmetic.** _Tough_ on whoever would take the damage: all damage prevented and one tough discarded (p. 44), except that a hero making a basic defense reduces by DEF first and **keeps** the tough if the result is 0 (p. 9 step 5, p. 44) — which is exactly a band boundary, and which the engine already gets right by returning early on `amount <= 0` (`resolve/event.ts:301`). _Overkill_ fills `overkillTo`/`overkillAmount` on the bands where the defender is defeated (p. 31), and is absent otherwise — that absence is the "the rest was lost" the design asks for. _Retaliate X_ on the defender is a fixed number, not a range: it triggers on "is attacked", not on damage (p. 38), so it is the same in every band — except that the character must still be in play after the attack (p. 38), so it drops to 0 in a band where the defender is defeated, and it is 0 outright against a `ranged` attacker. Read it through the same path the resolver uses (`keywordTotal(..., "retaliate", ...)` and the `ranged` check, `resolve/event.ts:406-411`). _Stunned_, _confused_, _stalwart_ and _steady_ change **nothing** in the defend preview and must not be mentioned there: a stunned enemy's attack is replaced by discarding the status before any of this, so no defend choice ever opens (p. 41 "Stun, Stunned"); confused cancels a scheme, not an attack (p. 13); stalwart (p. 40) and steady (p. 41) only govern whether those statuses stick, and steady means "stunned" must always be asked of the engine's own check rather than of `statuses.stunned > 0`. They belong to W7's "queued this phase" list (an activation that is going to be cancelled), not to W6.

## 4. Decisions to settle

- **Advice text.** Deck notes (D14, P04), "Why this matters" (P13) and "Table talk" (P08) are strategy advice, not rules. If kept, each needs a named heuristic in a tested view model, worded as a suggestion, and never using hidden information. Or drop them.
- **Scenario and hero blurbs** (D02, D03, P03). They aren't in `@mc/content`. Either write short original descriptions, or show only data (stages, HP, sets, obligation, nemesis). Don't copy FFG card or product text into them.
- **Keyword glossary wording** (S6). Short paraphrases with an RRG 1.8 page cite, rather than transcribing the RRG.
- **Auto-resolve and auto-defend** (P12, D10, P15). A client preference that answers a choice for the player is still the player's command. It must issue ordinary commands and never change engine behavior. Decide whether it's in scope before Phase 5 makes seats remote.
- **Heroic difficulty** (D05). Not a Core Set mode and not in the engine. Leave it out, or draw it unavailable.
- **Concede** (W4): DECIDED 2026-09-17 — an engine outcome (`concede` command, `conceded` result), per S5.9.
- **Pass-and-play handoff** (P16, L07). Only meaningful with several humans on one device, which means hiding hands between seats. Decide whether that's Phase 4 or Phase 5.
- **Owned-card collection** (D14). With only Core implemented every card is "owned". Probably out of scope until Phase 7 adds packs someone might not own.
- **Seed display** (D05 shows `4F2C-91A7`). Today seeds are whole numbers typed and shown as digits (`view/seed.ts`). A hex display needs a lossless round trip with what the player types back in.
